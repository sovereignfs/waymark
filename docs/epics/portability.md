# Epic 15: Portability

## Status

📋 Planned.

## Overview

A person can take what is theirs and bring it to another Waymark: one ZIP of JSON and files, built by a job. Phase 1 covers places and check-ins; phase 2 adds
trips. This is the app's own format, separate from the Swarm import (epic 8).

## Tasks

#### ✅ 15.1 — Export

**Goal:** a person's data in one file. **Design:** §22. **Depends on:** 5.3, 1.6.

**Technical:** a job builds a ZIP: `waymark.json` (`format`, `version`, profile, settings, places, check-ins with companions and links) and the photos as files;
stored sealed under `/data/exports`, downloadable from Settings > Data within a day, then deleted; no one else's email; noted on core's activity page once
14.1 is in.

**Accepts when:** an export of a seeded person holds every place, check-in and photo, and its JSON validates against the format's schema.

**Done as, for phase 1's data (trips join in 15.3):** **`src/portability/format.ts`**, the one definition of the file, used to write it and (15.2) to read it: `format: "waymark-export"` and a `version` first; the profile (name, units, first day of the week, sharing default: **no address**), the choices of what is emailed, `places`, `checkins` (with companions, source, the import's own id, and the ids of their photos) and `photos` (`{ id, file, type }`). `parseExport` checks a file **whole before anything is written**: the format and version first (a different format is "not a Waymark export"; a higher version is refused with "update Waymark, or export again from this version"), then **every place and check-in by the same rules a device's change meets** (`checkins/validate.ts`), then that it hangs together (ids that are ids and not repeated, every check-in at a place the file has, a photo on one check-in at most, every listed photo a file named `photos/<uuid>.<webp|jpg|png>` and named by a check-in, at most 500,000 of each), and its sentences repeat nothing of the file. **`export_job`** (migration `0013_export_job`: owner, status `queued`, `running`, `ready`, `failed` or `expired`, size, times and a lease; nothing in the row says what is in the file). **`src/portability/export.ts`**: a person asks (one at a time; a second while one is queued or running is "busy"), a worker **claims it by a lease** in one statement as the import's and the mail's are, and builds the ZIP **as a stream into a sealed file of its own** under `<data>/exports` (the same chunked sealing as an uploaded import, bound to the file's id and each chunk's place, so a decade of photos is never whole in memory and a file touched on disk does not open); **the photos are written first, each as the file it is, and `waymark.json` last, listing exactly what was written**, so a photo that went between the list and the file is never named and missing; a photo taken offline that has not reached the server is not in the file and its check-in still names it (an import tolerates that); the lease is kept every 25 photos. It is **ready for 24 hours** and then not downloadable even before the sweep, which deletes the file and marks it expired (the record stays a week); a file no request names is swept once it is an hour old; a build that throws ends as failed with its file removed and logs nothing of the data. `People.deletePerson` removes a person's exports, files and rows (the deletion test lists the table and seeds a built export for each of two people). **`/api/exports`** (`GET` list; `POST` asks, five an hour for an account, 409 with a sentence while one is being made) and **`/api/exports/[id]`** (`GET` streams the ZIP from the sealed file a chunk at a time as an attachment, `private, no-store`, `nosniff`, and a policy that lets nothing in it run; `DELETE`), for an account only, `Origin` checked on a write, with a test that calls each as a second person: **another person's export, one that is not ready, one that has run out and one that never was are the same answer, not found**. **Settings > Data** has an _Export my data_ button, a list that looks every three seconds while one is made, _Download_ and _Delete_. **My own ZIP writer and reader (`src/portability/zip.ts`), because the first one did not do what the format needs:** the streaming writer of the library tried first (`fflate`) writes the number of entries in 16 bits and no ZIP64 end record, so an archive of 70,000 files read back with 4,464 (found by writing 70,000 and asking `zipinfo -h`, and the system `unzip` found them all only by scanning), which would have silently dropped photos from the exports of the people with the most. The writer stores a file whole (so its size and checksum are known and no data descriptor is needed), stores photos and deflates the JSON, and writes the ZIP64 end record for more than 65,535 entries and a directory or offset past 4 GB; the reader opens a file on disk by its directory, never whole in memory, reads ZIP64, **refuses encryption, any method but stored and deflate, a repeated name and a directory that points past the file, refuses an entry larger than the caller allows before expanding it, bounds what an entry may expand to (a zip bomb whose small stored size hides a huge one is refused), and checks every size and checksum**; 15.2 and the Swarm reader (8.2) use it. `fflate` stays as a **development dependency** only, an independent reader and writer to check this one against. **Seen** on a `file:` database, sqld and PostgreSQL (230 tests in the data-layer files on each; 32 in `src/portability`): the file holds every place, check-in and photo of a seeded person and its JSON passes `parseExport`; a photo's bytes equal what the server holds; the photo that never uploaded is named and not in the list; **the file holds nothing of a second person (their places, notes, photo, name or address) and no address at all, the person\'s own included**, and the second person\'s own export holds hers and none of the first\'s; the file on disk is unreadable and not a ZIP without the key; one at a time for a person and another not held up; two workers at once build it once; owner only, ready only, within the day only; deleted at once by the owner and by no one else; removed with the person; a build that cannot be made ends failed with no file; the ZIP written and read back, read by `fflate` and found sound by `unzip -t`, an archive written by another writer read, **70,000 entries written with the ZIP64 end record and read back whole, and `zipinfo` says 70,000**, a changed byte caught by the checksum, a bomb, an over-large claim, encryption, an unknown method and a repeated name refused; **in Chromium (`e2e/export.spec.ts`):** a person checks in, asks in Settings > Data, waits for it, downloads `waymark-export-<date>.zip`, and the JSON holds that place and check-in and no address; then deletes it. Each safeguard was taken out in turn and seen to fail its test (the ZIP64 record, the owner in the download). **Found while doing it:** a browser test of the notices that built "yesterday" as 1.2 days ago failed between midnight and 05:00, when that is the day before; it uses yesterday at noon. **Left out:** a line on core\'s activity page (14.1), trips (15.3), and offsets past 4 GB, which the writer and reader handle by the format but which no test writes (it would need 4 GB of data); WebKit was not run.

#### ✅ 15.2 — Import

**Goal:** a file made into new rows. **Design:** §22. **Depends on:** 15.1.

**Technical:** upload a Waymark ZIP; validated whole before anything is written; places and check-ins made new for the importer, skipping ones already there
by id, photos through 3.2; a newer version refused with a sentence; a job for large files, with 8.1's resumable shape.

**Accepts when:** export, import into a second account, export again: the two exports match but for ids and times; importing the same file twice creates
nothing the second time.

**Done as:** a Waymark file is **a reader of the import job (8.1)**, as the task says: `src/portability/reader.ts`, registered in `readers.ts`, uploaded to `/api/imports?source=waymark` and shown in Settings > Data (_Import a Waymark file_: a file chooser, a status that looks every two seconds, _Cancel the import_, and a sentence for a file that is refused). So everything the job does is done for it: a lease, steps of 25 with the cursor kept after each, a restart carries on, a cancel, the file deleted at the end, a notice in the bell (and by email where wanted). **Validated whole before anything is written:** `open` opens the ZIP by its directory, reads `waymark.json` within 256 MB and runs `parseExport` (15.1's: the format and version, every place and check-in by the rules a device's change meets, that the file hangs together), and checks that every photo it lists is a file of the ZIP no larger than a photo may be; a file that is not a ZIP or has no `waymark.json` is "not a Waymark export", JSON that is not JSON is "could not be read", a version above this one is "from a newer version of Waymark… update Waymark, or export again", and **one invalid check-in anywhere, even the last, refuses the file and none of the others is made** (tested with thirty good ones and one bad). **New rows for the importer, once:** the job gives a place, a check-in and a photo ids made from the importer's account and the file's own ids (`idFor`), so the ids here are not the file's, a second import of the same file makes the same ids and **creates nothing**, a place the importer renamed keeps their name and a check-in they deleted stays deleted (tested). **The importer's profile and settings are not touched.** Changes to the job (8.1's) to carry a file with photos and places of every kind: **a reader holds a session** (`open(file)` once for a run, `checkins({cursor, limit})` for each step, `close()`), so a ZIP is opened once and not for every step; an item carries its own `source` (a Waymark file keeps what each check-in was: live, manual, imported from Swarm), its `photos` and its place's `source`, zone and `key`; **a Swarm check-in in a file keeps its Foursquare id on the row** (`rowExternalId`) and not the file's own; a reader may throw an `ImportRefusal` whose sentence is what the person is shown and what the bell says; and a read may hold **places with no check-in**, after the check-ins in steps of their own, so a place made and never checked in at comes too (found by the round trip: "Never Visited" was lost). **Photos:** read from the ZIP **only for a check-in that is going to be made**, one at a time, and **stored for the importer before the check-in that names them** through the media store (3.2: judged by their bytes, re-encoded, counted against their limit), so a check-in never names a photo that is not there; one that cannot be stored (not an image, over the limit) is left off the check-in, counted as one that could not be kept, and the check-in is still made; a photo the file names and does not hold (it never reached the server) is not brought. **My own ZIP code** (`zip.ts`, from 15.1) does the reading: ZIP64, a bound on what an entry may expand to, every size and checksum checked. **Seen** on a `file:` database, sqld and PostgreSQL (240 tests in the data-layer files on each; 42 in `src/portability`, 29 in `src/import`): **export Ada, import into Grace, export Grace: the two match but for ids and times** (every place including one never checked in at, every check-in with its note, companions, source, zone and offset, and every photo: the same type, and decoded the same picture, 40 by 30), with Grace's ids not Ada's, Ada's photos still Ada's, a Swarm check-in keeping its Foursquare id, one notice for Grace and the file gone; the same file again makes nothing (`checkinsDone` 0, five skipped) and leaves a rename and a deletion; Grace's name is still Grace's; a stop during the first step carries on from the cursor and makes 80 check-ins once; and every refusal above, a photo the ZIP does not hold, a photo larger than a photo may be, an HTML file named as a photo (check-in made, photo left off and counted), and a cancel. **In Chromium (`e2e/import-file.spec.ts`):** a file that is not a ZIP is refused with its sentence, a file from version 99 is refused and says to update, a good file imports ("Imported: 3 check-ins and 1 places") and its check-ins are in the timeline, and the same file again says three are already here and adds none. **One thing the round trip shows and does not fix:** a photo goes through the media store's re-encoding (WebP at quality 82, metadata removed) every time it is stored, so an exported photo that is imported is the same picture and **not the same bytes**, and a photo exported and imported many times loses a little each time. A file already of this app's own making could skip the re-encode; that would make the store trust a file's claim, which 3.2 refuses to do, so it is left. **Left out:** trips (15.3); a line on core's activity page (14.1); the Swarm reader (8.2) and the generic import screen (8.3); the same Foursquare id arriving by a Waymark file and by a Swarm import is refused as a duplicate, not merged; WebKit was not run.

#### ✅ 15.3 — Trips in export and import

**Goal:** phase 2's data in the file. **Design:** §22. **Depends on:** 15.2, 9.6, 10.3.

**Technical:** trips where the person is an Organizer or Traveler, whole (stops, days, items, trip places, links, attachments as files; members by name
only; the person's own and shared check-ins as the journal shows them); import makes each a new trip with the importer as sole Organizer, the other members'
names kept in its description.

**Accepts when:** a trip round-trips with its plan and files, and no other member's email or unshared check-in is in the file.

**Done as:** **The file is version 2** (`format.ts`; a version 1 file is still read, with no trips; a higher one is refused with the same sentence as before). `trips-format.ts` (pure) defines and checks the trips section: for every trip where the person is an **Organizer or a Traveler**, the trip (name, description, colour, whether it was marked ready), its **members by name and part only**, its own places, stops (dates, note, order), **all its days** (so an item can name its day; with a title and notes where it has them), items, links, **attachments as files** under `attachments/<id>.<pdf|webp|jpg|png|zip>`, the ids of the person's own check-ins linked to it, and **the check-ins other members shared with it, as text, by the author's name** (no photo, no id, no address of theirs). `parseExport` checks them **whole, before anything is written**, by the rules the server applies (places by `validatePlaceRow`, items by `checkItem`, links by `checkLink`, the stops by `checkStops`) and that they hang together (a stop at a place of the trip, a day at a stop of the trip and on a date it covers, an item on a day and at a place of the trip, an attachment's file named once, a listed check-in the file's own), with a bound on every list. A **stop's position is the plan's own order key** (digits), not a fractional-index key as an item's and a link's: found when the first round trip was refused. **Export** (`gatherTrips`): the trips are read as the same snapshot a device is given (`pullTrips`, 6.6), so every reader names the account and a role, and **a Follower's trips are not in the file** (it is not theirs to take); the person's check-ins keep their link to a trip that is in the file and lose it to one that is not; the attachments' files are written before the JSON that lists them, and an attachment whose file went in between is not named (the photos' rule). **Import** is a stage of the import job (8.1), after the last step of check-ins so that they are there: `ReaderSession.trips()` hands over the trips and a way to read their files, and `src/import/trips.ts` makes **each a new trip with the importer as its only Organizer**, the other members' names and parts in its description (after the file's own, within its limit, and without the importer's own name), in **one transaction** (the trip, the importer's membership, its places, stops, days with their words, items on the right days, links, attachments with their files stored first), with **ids made from the importer and the file's own (`idFor`, which moved to `import/ids.ts`)** so that the same file again makes nothing, and the importer's check-ins that fall within its dates are linked by the same auto-link, asked for in that transaction. The job counts the trips (`import_job.trips_made`, migration `0024_importtrips`), says so in the bell ("…with 1 trip") and Settings > Data; a file whose attachment is missing from the ZIP is refused at the door. **Seen**, on a `file:` database, sqld and PostgreSQL (the whole suite, 1549 tests; 28 of them new): the export holds the trip whole with its files byte for byte (a PDF as it is) and passes the format's own check; **the members by name and part only, what Grace shared as text by her name, her private check-in not in Ada's file (and in her own), no `@` anywhere, nothing of a trip Ada follows or is not in**, and a Follower's own file has no trips; the import makes Hal's trip with him as its only Organizer, the description naming the others, the dates, the plan, words, items on the right days, links and the files, and **Hal's export matches Ada's but for ids, members and what others shared**; the check-in of his that falls in its dates is linked once the job has run; the same file again makes none, and a version 1 file reads as before; a trip that cannot be made leaves no row of it; the importer's own file does not list them; every invalid trip is refused whole (14 ways). With each of these taken out one test fails: the Follower filter, the relink request and the importer's name (found missing by the first run and tested since). **One guard is defence in depth**: the check that the trip is not there yet before its files are stored (the transaction checks again). **Left out:** the importer's **manual links** are not carried (the file keeps the links, the import lets auto-link decide); **what other members shared** is in the file for the person's own record and is not brought (it is theirs, and the journal that would show it is 11.5); a trip the importer deleted is **made again** by importing the file again; the importer's **trip limit** is not applied to a file's trips; a Swarm file has no trips; and a line on core's activity page for the trips (14.1) is the import's existing one.
