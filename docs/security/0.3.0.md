# Security review: phase 3 (0.3.0)

What phase 3 adds is **the device acting on its own**: Web Push (12.4), reminders (13.4), Today and Trip Mode (13.1 to 13.3), and **a trip's map
kept on the device by the service worker** (13.5). This is the review of `0.1.0.md` and `0.2.0.md` repeated for it, in the same form: the rule,
where it is held, what was found, and fixed or recorded. The two earlier reviews are the baseline.

**State of the run:** `pnpm test` 1817 passed, 4 skipped (four tests that belong to another database leg); `e2e/offline-trip.spec.ts`, `tripmode.spec.ts`
and `tripmap.spec.ts` pass in Chromium and WebKit in this run; the notices spec (`notices.spec.ts`) covers the bell and the push settings.

**Not covered.** **No real browser has received a push from a real push service yet** (12.4's own note): the encryption, the signing and the
delivery are tested against a fake service that decrypts as a browser does (`push.test.ts` "delivers an encrypted push to the device's own push
service, and the browser reads exactly a kind and a path"), not against Google's, Mozilla's or Apple's. Directions (13.3) was not tried on the
iOS Simulator. Nothing was run on a live instance (16.5).

## 1. Web Push (DESIGN.md §17.3)

- **What a push carries is a kind and a path of this app, and nothing else.** `payloadOf(kind, path)` is `{k, p}` (`src/push/outbox.ts`): **no
  place, no person, no trip name, no time**. The words are the worker's own, chosen by the kind (`src/sw/source.ts`), so a push service, which
  sees the traffic and the size, learns that Waymark has something for this device, and nothing about what. The worker shows a push with any other
  field, or a kind it does not know, as the plain sentence it falls back to, and follows only a path of this app (`source.test.ts` "says nothing of
  what a push carries beyond the kind and the path…", "is shown even when the data cannot be read, and follows only a path of this app").
- **The payload is encrypted to the device** (RFC 8291) and signed with the instance's VAPID key (RFC 8292); the browser reads exactly a kind and a
  path (`push.test.ts`).
- **A subscription is only ever for a browser's own push service.** The address must be `https`, with no name or password, on a host of
  `PUSH_HOSTS` (Firebase Cloud Messaging, Mozilla, Apple, Windows), because **the server will POST to it**: an address a person could point
  somewhere else would make the server send to it, which is a server-side request a person chose. It is checked **twice**: when the browser
  subscribes (`push.test.ts` "is subscribed only to a browser's own push service…", "is refused for a host that is not a push service…") and
  again when a push is sent, through the one outbound helper (`0.1.0.md` §4), so a row that somehow held another address sends nothing and the
  device is removed ("never sends to an address that is not a push service's"). Up to ten devices an account.
- **Sealed.** The address and the keys that encrypt to that browser are sealed (`SEALED.push_subscription`); the database knows the owner and a
  hash of the address, which makes turning it on again in the same browser one row. They go with the person (`people.test.ts`).
- **The VAPID key is derived from a secret** (`WAYMARK_VAPID_PRIVATE_KEY`, at least 32 characters, made once by the instance's manifest, with no
  default); push is off with none, and **the secret is never in an error, a log or the browser** (`push.test.ts` "wants a secret of enough length
  and an address for the app, and says nothing of the value"; "writes nothing to any log: not an address, a key or a payload"). The public key a
  browser subscribes with is public by nature.
- **A push is raised in the change's transaction, and not for the person who acted**: "stands or falls with the change: rolled back, no push is
  queued"; "the sender is never told". A device only gets a kind the person asked to have by push; **a pass with two workers sends once**, and a push
  another worker holds is not taken (`push.test.ts`). A device that the service says is gone (404, 410) is removed; one that is busy or failing is
  tried again after a growing pause, and a push too old to be of use is dropped.
- **`/api/push`** is an `account` route: the account's own devices only, with a body that is exactly a subscription.
- **Finding 1.1 (recorded).** A push service sees **that** a device is told something and **when**, and the size of the payload, which is roughly
  constant. It cannot see a kind or a path, which are inside the encryption. This is inherent in Web Push. **The user guide and the settings page do not say it yet**; it is written with the documents (16.3).
- **Finding 1.2 (recorded).** A subscription belongs to the browser, and a push shows words of the worker's own for a kind; **it names a path and a
  kind, never a person or a place**, and opening the path needs a session. A device that is shared and still subscribed shows the first person's
  kind of notice ("something to see on a trip") to whoever holds it. Turning push off is one tap in Settings and removes the device with what was
  waiting for it ("is turned off by its owner alone, with what was waiting for it"). Whether signing out should turn it off is a design question
  left open (DESIGN.md §28 is the place to settle it).

## 2. Reminders and Today (DESIGN.md §14, §17, §13)

- **Who is reminded is decided by role and by what the member said:** the evening before, to every member who **goes**, once, and not to a Follower
  nor before 18:00; not to an Organizer who does not go, nor for a trip still being planned; half an hour before a fixed item, to those who go
  (`reminders.test.ts`). Nobody is reminded of an item they marked done, and an item moved to a new time is a new reminder. A morning digest only
  to those who asked, in one line.
- **A member's reminders are theirs for the trip** (lead time, flexible items, none at all), changed **through the trip's operations**, for
  Organizers and Travelers alone, within limits, and **go when the person leaves or the trip is deleted** (`reminders.test.ts`; `people.test.ts`
  covers the tables).
- **Claimed in the database:** a reminder is sent once with two workers running at the same moment, and what was sent is forgotten after a month
  (the `jobs` claim, as the outbox's). **A job safe to run twice** is the rule, and it is the test.
- **A reminder reaches the bell always, and a device by push only if the person turned push on and wants the kind by push**
  (`reminders.test.ts`): nothing is pushed unasked.
- **Today** (13.1) is a pure figure computed on the device from the person's own store (`src/today/`), shared by the device, the server and the tests;
  it asks no server.

## 3. A trip's map on the device (DESIGN.md §14.5, 13.5)

- **The cache is an allow-list, and the map's is the only thing kept beyond the shell.** The tiles are kept in a cache of their own
  (`waymark-tiles-v1`), by the worker, **only for addresses of the map**: a tile `/api/map/tiles/z/x/y`, the style for a theme, a font's glyphs. The
  pattern is anchored and bounded (`MAP_FILE`: one or two digits of zoom and seven of x and y; a font stack of up to 64 safe characters), and
  `source.test.ts` holds that **any other address, another origin's and a path that only looks like a tile are left out**, and that **a tile that was
  not named is not stored just because the map asked for it**.
- **The page asks by a message and the worker obeys only what it is told it may:** `keep-map`, `drop-map` and `map-status`; **any other message is
  ignored** (`source.test.ts` "ignore a message that is not one"). A message to the worker can only come from a page of this origin (the browser's
  own rule), so the page is the only asker; a page of a script that got in could ask for tiles of the map and nothing else.
- **Bounded:** the page asks for at most `TRIP_TILE_LIMIT` (600) tiles for a trip, zooms 3 to 14 around its stops; the worker keeps up to a bound and
  counts what the server did not have ("are kept up to a bound, and a file the server does not have is counted and not kept"). The server's side
  of a tile request is the same `/api/map/tiles` route as any map's, an `account` route limited to 1500 a minute for each account.
- **What a kept tile holds is public** (the map's own, the same for everyone), and the cache holds **no page, no answer of the API and no row of a
  person**; the push handler and the cache handlers have no access to the device's store (`source.test.ts` "reads no device store and names no
  check-in, address or note: the source says none of them").
- **Finding 3.1 (recorded).** **Which tiles are kept tells where a person's trip is**, to anything that can read the browser's Cache Storage:
  the area of a trip's stops at fine zooms is in the names of the cached requests. That is **the same exposure as the device's store**, which holds
  the trip itself (§2 of `0.1.0.md`), and no more: a person who can read one can read the other. Sign-out deletes the device's store **and the
  kept maps** (`forgetKeptMaps`, called by the account menu's Sign out, `src/auth/screens/AccountMenu.tsx`); they are also listed and removable in
  Settings, Device.
- **Finding 3.2 (recorded).** If the session **expires without a sign-out** (the cookie ends, the page was not open), the kept tiles stay until the
  person opens the app and signs out or removes them. They hold nothing but the tiles' bytes and their names (3.1). The device's store is the larger
  exposure in that case, and it is under the same rule.
- **Finding 3.3 (recorded).** The worker answers a tile from the cache **with no session check**, as it answers the shell: that is what working
  offline means. The same tiles cannot be had from the server without one (`/api/map/tiles/…` is an `account` route), so a person who is signed out
  and online gets none from the network, and a person offline gets the ones their own device kept.
- **Finding 3.4 (FIXED in this change; found while writing this review).** A map that could not load its code (offline at the moment the chunk was
  first needed, or a chunk gone after an update) replaced the whole screen with the error page. Trip Mode and Home draw their maps on screens the
  person needs when travelling, which is exactly when the network is not there: `src/screens/loadMap.ts` now draws nothing in place of the map and
  leaves the list, which is the same information. Held by `checkin.spec.ts` (the check-in sheet's own offline spec, which failed before the change in a
  full run and passes after) in Chromium and WebKit.
- **Finding 3.5 (FIXED in this change).** `worker-src` is now `'self'` alone, with MapLibre's worker served from the app (`0.1.0.md` 5.1). The
  service worker and the map's worker are the only workers; no worker is made from a string.

## 4. Directions (13.3)

- **Directions is a hand-off to the device's own maps, and nothing is fetched by Waymark** (`src/directions/directions.ts`): `geo:` on Android,
  `maps://` (Apple Maps) on iPhone and iPad, and elsewhere an OpenStreetMap link that opens in a browser. It is pure, so the device is given in and
  it is tested without one (`directions.test.ts`). **A name is one line of at most 100 characters with no control characters and is percent-encoded,
  so that a place's name cannot add a parameter or a scheme to the link**; a point that is not a point is no link. The app and the server make
  no request to a routing service.
- **Finding 4.1 (recorded).** The point (and the name) of a stop is **given to the maps app, or on other devices to openstreetmap.org, at the
  person's own tap**. That is what Directions is. It is the person's browser's request and not the app's or the server's (so the CSP and the
  outbound helper do not apply), and it is not logged. Not tried on the iOS Simulator (13.3).

## 5. Logs and errors

- **Logs hold no place names, points, notes, titles, search text, names or addresses**, only an id and a kind of failure; the push and the
  reminders' passes say how many they sent, will try again and gave up on (`push.test.ts` "writes nothing to any log"). The jobs' lines name counts
  (`src/jobs/index.ts`).

a real browser (12.4's open note), Directions on an iPhone (13.3), the update of a live instance with a backup first (16.5), and the sqld and
