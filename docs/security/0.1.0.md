# Security review: phase 1 (0.1.0)

A written review of what phase 1 builds (check-ins, places, the map, Home, the timeline, notices, export and import, sign-in locally and through
Sovereign), made against `DESIGN.md` §25 and the rules of `AGENTS.md`. Each area says what the rule is, **where it is held** (code and the test that
fails when it stops being true), what was found, and whether the finding was fixed or recorded and why.

**Method.** Reading the code that holds each rule, running the tests named below on the three databases' legs where the leg applies, and, for what
only a browser shows, the Playwright specs in Chromium and WebKit. A rule that a test does not hold is said so. **State of the run:** `pnpm test`
1817 passed, 4 skipped (four tests that belong to another database leg, `it.runIf(leg === …)`); the browser specs named in each section pass in both browsers.

**Not covered, and why.** The Swarm import's photos and its screen (tasks 8.2 and 8.3) are not built: 8.2 waits on a real export. The import job's
allow-list (`*.4sqi.net`, `*.foursquare.com`) is written but nothing reaches those hosts yet, so **its first real use is a review of its own** before
0.1.0 is published. Nothing in this review was run against a live instance (16.5).

## 1. Access (DESIGN.md §5.2)

- **Every page and route says who may use it.** `src/access/routes.ts` lists all 44 of them as `public` (with the reason, when a public route changes
  something) or `account`; `src/access/routes.test.ts` fails for a route with no rule, a rule with no route and a method that does not match, and
  holds each `account` route to `accountRoute` (session first, `Origin` checked on a write) and each page to `requireAccount()`.
- **A refusal reads as not found, and a person's rows carry `account_id` in the statement.** Every server test that needs the wrong caller goes through
  `src/access/two-accounts.ts` (real sessions on the leg's database); 11 test files call as the second person (settings, the route wrapper itself, place search, notices and
  their preferences, export and import, deleting a person, core's account-deleted notice, sync, the import's routes and trips).
- **The sync stream and the notices** are called as the second person in `src/sync/endpoint.test.ts` and `src/notices/http.test.ts`, which assert the
  answer for a row that is not theirs and that nothing changed.
- **Finding 1.1 (recorded).** `/api/auth/[...all]` is better-auth's own surface, listed as `public` with its reason; its routes are rate limited in
  the database (`rateLimit.storage: 'database'`), so the limit holds across processes. Better-auth's own tests are not ours to repeat; ours cover
  the sign-up policy, the invitation's token, linking and the password-less routes.
- **Finding 1.2 (recorded).** The rate limit is a fixed window (`src/limits/rate.ts`): a holder can do up to twice the limit across the edge of two
  windows. The price of one statement per count and no history; the limits are set for abuse, not as a quota.

## 2. Sealing (DESIGN.md §18)

- **What says where or what is sealed**: place names, points, addresses, notes, companions, profile names and emails, files. Written and read only
  through `src/crypto/sealed.ts`; the column type `sealed` is the only way the schema holds one (`src/db/schema/*/columns.ts`); `sealed.test.ts`,
  `envelope.test.ts` and `rotate.test.ts` hold the envelope, a wrong key, a tampered row and the rotation of a key (3.3).
- **No sealed field is a column in a `WHERE`, an `ORDER BY` or an index.** Search, distance, figures and the map work in memory on unsealed rows
  (the timeline, `src/screens/mapview.ts`, `src/figures/`). The one thing that is unsealed and tells a little is a row's date, its owner and the
  count of rows, which the design accepts (§18.1).
- **Finding 2.1 (recorded).** The device's store (IndexedDB) holds the account's rows **unsealed**, since the page needs them to paint. It is per
  account, holds only what the account may see, and is deleted at sign-out (`src/local/`). It is as safe as the browser profile; it is deleted
  at sign-out (`local.test.ts` holds that another account's store is left). Nothing to fix; the design says so (§14).

## 3. Files and uploads (DESIGN.md §18.3)

- **Judged by their bytes.** `src/media/detect.ts` reads the first bytes against a list per kind (photo, attachment, import); a name or a declared
  type decides nothing; what is not on the list is refused before it is decoded (`detect.test.ts`, `media.test.ts`).
- **Re-encoded with every piece of metadata removed** (`src/media/images.ts`), so a photo's position, camera and time never reach another person;
  **sealed on disk** under `/data/media` and **served only through `/api/media/[id]`** after the access check. The thumbnail is made by the server
  (`thumb.test.ts`).
- **Followers never receive an attachment** (phase 2's review, §5 of `0.2.0.md`); phase 1 has no sharing, so a file is its owner's alone.
- **A file is never a page** (`fileHeaders`, `src/media/http.ts`): the stored type and no other, `nosniff`, `Cache-Control: private`,
  `Content-Security-Policy: default-src 'none'; sandbox` and `Cross-Origin-Resource-Policy: same-origin`, so nothing in a file may run, load or frame.
- **Finding 3.1 (recorded).** A PDF attachment (phase 2) is stored as it was sent (sealed), not re-encoded, and is served `inline` under that
  sandbox policy. Re-encoding a PDF would be more than it is worth; the risk left is the viewer's own PDF engine, which the sandbox policy
  narrows and does not remove.

## 4. The server's outbound requests

- **One helper.** `src/security/outbound.ts`: configured hosts only (exact or `*.example.com`, never the bare name), refusal before a connection to a
  host that is not on the list, a redirect only within it, never a private address (checked **at connection**, in the lookup the connection uses,
  so a name that answers differently to a check and a connection reaches nothing), a timeout over the exchange, a size cap, https unless the
  operator's own host says otherwise (`outbound.test.ts`). Its users are place search (`src/places/`), the tile upstream (`src/map/`) and push
  (`src/push/`); the import's photos will be the fourth.
- **Finding 4.1 (recorded).** **SMTP (`src/mail/smtp.ts`) and core (the SDK) are not through the helper:** they are protocols and clients of their
  own, to the one host the operator configured. They have timeouts of their own, and nothing a person typed chooses the host. If a setting could
  ever name a host from a person, it would have to move to the helper first.
- **Finding 4.2 (recorded).** The place search's query is a place name. It is sent to the configured search host and to nobody else; it is not
  logged (a log holds an id and a kind of failure) and the result is cached for a day in memory only.

## 5. The browser: CSP and no third-party request

- **`src/security/csp.ts`**: scripts only with the request's nonce (`'strict-dynamic'`, no inline handler, no `eval` in production); style
  elements carry the nonce; `img-src 'self' data: blob:` (a photo taken offline and not yet sent); `connect-src 'self'`; `frame-ancestors 'none'`;
  `form-action 'self'`; `base-uri 'self'`; `object-src` and `frame-src` `'none'`; `upgrade-insecure-requests` over https. With it:
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` that closes the camera, the microphone and the rest and
  leaves `geolocation=(self)`.
- **Finding 5.1 (FIXED in this change).** `worker-src` was `'self' blob:` because MapLibre made its web worker from a blob. The app now serves the
  worker's two files itself (`/api/map/worker/[file]`, `src/map/worker.ts`) and gives it to the map as `workerUrl`, so **`worker-src 'self'`**
  is the whole policy, and the test (`csp.test.ts`) holds it. The map screens (Map, Home, the check-in sheet's map, a trip's map, Trip Mode and a
  trip kept offline) pass in Chromium and WebKit under it. A `blob:` worker would have let a script that got in make a worker of anything it
  wrote.
- **Finding 5.2 (recorded).** `style-src-attr 'unsafe-inline'`: React's `style` props and the design system's overlays position things with
  attributes. An attribute changes how something looks and cannot run anything; scripts and style _elements_ stay under the nonce.
- **Finding 5.3 (FIXED in this change).** A map's chunk that could not be fetched (no network at the moment the map was first drawn, or a chunk
  gone after an update) went to the error boundary and replaced the whole screen with "Something went wrong". Not a leak, but **a screen that
  depends on a third thing it cannot reach is a defect of the same family**: `src/screens/loadMap.ts` makes the map draw nothing and leaves the list
  beside it, which is the same information. Found by a browser spec (`checkin.spec.ts`, offline) that failed in a full run, with and without the
  CSP change.
- **No request leaves the page for another origin.** The specs that draw a map or the first pages watch the origin (`watchOrigin`)
  and asserts none (`map.spec.ts`, `tripmap.spec.ts`, `smoke.spec.ts`; `helpers.spec.ts` tests the watcher itself).
- **What people write is rendered as text.** The one `dangerouslySetInnerHTML` in `src` and `app` is the layout's theme script (`app/layout.tsx`): a
  constant of the app's own, with the request's nonce. No `innerHTML`, `eval`, `new Function` or `document.write` anywhere (searched).

## 6. Sign-in, Sovereign and core's notices

- **Sign-in** is better-auth with the Drizzle adapter: passwords hashed by it, a session cookie with the `waymark` prefix (`Secure` over https),
  origin check on (`disableOriginCheck: false`), sessions fresh for ten minutes for what asks (unlinking Sovereign, deleting without a password).
  Verification and reset by mail only where there is mail; a reset link is single-use, lasts an hour and ends every other session.
- **An account is known by its better-auth user id**; a Sovereign login is matched by its `sub`, **never by an email** (`disableImplicitLinking`,
  `allowDifferentEmails: false`); linking is from a signed-in session; `requireIdTokenVerification` is on, so a discovery document without keys is
  not trusted. The core's tokens are kept encrypted (`encryptOAuthTokens`).
- **The sign-up policy** (`WAYMARK_AUTH_SIGNUP`: `open`, `closed`, `invite`, default `invite`) is one hook in `databaseHooks.user.create.before`,
  so it holds for every way an account comes to be; a Sovereign login is let in whatever it says, since core decides who signs in to it.
- **Finding 6.1 (recorded).** An invitation link that has not been accepted can be used to make **more than one account** until it is accepted
  (the token opens sign-up; the invitation is spent when it is accepted into a trip, not when the account is made). The link goes only to its
  holder, it is single-use for the trip, and the sign-up route is rate limited; a design change (spending it at sign-up) would make a failed
  sign-up burn it. Recorded for phase 2's review (`0.2.0.md` §4), where invitations are built.
- **Core's notices** (back-channel logout, account-deleted: `/api/sovereign/*`) are `public` with the reason that the signed token stands in for a
  session; both are checked by `@sovereignfs/sdk`'s `verifyLogoutToken` and `verifyAccountDeletedToken`, and an account-deleted notice removes the person through `People.deletePerson`
  (`src/sovereign/delete-account.ts`, tested). **Bell, email and activity** to core are best effort: a call that fails, is refused or is not
  supported changes nothing but that call (§19.4).

## 7. Deletion (DESIGN.md §6.4)

- **`People.deletePerson`** (`src/sovereign/people.ts`) removes everything of an account, files included, and is safe to run twice;
  `people.test.ts` seeds one of each table's rows and checks that nothing of the account is left, on the three legs. **A new table is handled
  there, exported and imported, in the same change**, with a test.
- **Finding 7.1 (recorded).** A file's bytes are removed after the rows, so a crash between leaves a file nothing names. The media store's orphan
  sweep (3.2, run by the jobs, `src/jobs/index.ts`) removes a file no row names; meanwhile it is sealed and no route reaches it.

## 8. The service worker and the device

- **The cache is an allow-list** (`src/sw/`): the shell page, the app's own static files, and, from 0.3.0, a trip's map tiles. **No page or
  answer with a person's data is ever cached**: `src/sw/source.test.ts` ("caches nothing outside the allow-list, whatever a person does: pages,
  answers of the API, a place, a note") fails for one, and the worker's source is tested to read no device store and name no check-in, address or
  note.
- **Sign-out deletes the account's database from the browser** and leaves another account's (`local.test.ts`); the shell stays (it has nothing of
  anyone). A push shows words the worker writes itself from the kind it names; any other field is not shown (`source.test.ts`).

## Result

Two findings fixed (5.1, 5.3); the rest recorded with the reason they stand. **Before 0.1.0 is published:** the import's allow-list and photos
(8.2, 8.3), a pass on a live instance (16.5), and the documents (16.3) remain; this file is amended, not replaced, when they are done.
